# F-010 补充：广告配置（Ad Unit ID 等）的远程可配方案

> 回应问题：广告 ID 等配置是否灵活可配？靠改 App 还是靠管理平台下发？
> **结论：当前 PRD 完全没有定义广告配置的来源与变更机制，这是一处收入级风险缺口。建议改为「管理平台下发为主 + App 内置兜底」，做到不发版即可换广告单元、调频次、紧急熔断。**

---

## 一、现状缺口（先说问题）

| 缺口 | 说明 | 风险 |
|---|---|---|
| **ad_unit_id 来源未定义** | F-010 只在 `banner_impression` / `interstitial_impression` 事件属性里出现 `ad_unit_id`，没有任何章节定义它由谁配置、存在哪里 | 研发默认会**硬编码**在 `strings.xml` / 常量类里 |
| **变更必须发版** | 若硬编码，换广告单元 = 重新打包 + 提审 + 用户更新 | 东南亚用户更新滞后通常 1~2 周以上，期间该广告位**收入归零** |
| **无紧急熔断能力** | AdMob 单元被政策停用（电池类 App 属于易受限行业）、或某单元被判定无效流量时，无法快速下线 | 持续请求已停用单元 → 填充率 0 + 账号信誉受损，严重时会牵连整个 AdMob 账号 |
| **频次/场景写死** | `interstitial_impression` 有 `trigger_scene`、`session_event_count`，说明有触发逻辑，但触发场景和频次上限无处可配 | 想调"插屏每天最多 8 次"必须发版，而这是 eCPM 与留存平衡的核心调优手段 |
| **与埋点配置混为一谈的风险** | 10.3.3 的远程配置只服务埋点；10.1 原则 5 要求"与广告系统隔离" | 若后续把广告配置也塞进 `/analytics/config`，则**用户关闭埋点后广告配置也拉不到**，变现链路被埋点开关牵连 |
| **看板无法归因** | 10.5 要求看 eCPM、展示量，但若事件只带可变的 `ad_unit_id`，换 ID 后历史曲线断裂 | 需引入稳定的 `placement_id` 作为聚合维度 |

## 二、推荐方案：三级配置 + 管理平台下发

### 2.1 配置优先级链（从低到高，逐级覆盖）

```
L0  App 内置默认值（打包进 assets / remote_config_defaults.xml）
      ↑ 保证首次启动、无网、服务端故障时有可用广告（不能是空值）
L1  服务端下发：全局默认（按 app_version 生效范围）
L2  服务端下发：国家/地区维度（country = ID / VN / TH / PH / OTHER）
L3  服务端下发：广告位维度（placement）
L4  服务端下发：用户分群（is_pro / 新用户 / 实验分组）
L5  运营临时覆盖（紧急熔断、降级）
```

**解析顺序**（客户端）：先取 L0 内置 → 应用 L1 → L2（国家匹配）→ L3（广告位）→ L4（分群）→ L5（最高优先级覆盖）。

### 2.2 配置内容（远不止 ad_unit_id）

| 配置项 | 说明 | 为什么必须可配 |
|---|---|---|
| `ad_unit_id`（Android / iOS 分开） | 广告单元 ID | 核心诉求 |
| `placement_id` | **稳定的广告位标识**（如 `banner_home`） | 换 unit_id 时看板不断裂，埋点按此聚合 |
| `enabled` | 广告位开关 | 单个位出问题单独下线，不影响其他位 |
| `network` / `mediation` | 广告平台（AdMob / 聚合平台） | 未来接多家 waterfall |
| `frequency_cap` | 每会话 / 每日上限、最小间隔秒数 | eCPM 与留存的核心调优手段，需频繁试 |
| `trigger_scenes` | 插屏触发场景白名单（对应 `interstitial_impression.trigger_scene`） | 场景效果差异大，需按数据调整 |
| `first_launch_grace_minutes` | 新用户前 N 分钟不出广告 | 保护首日留存 |
| `load_timeout_ms` / `retry_count` | 加载超时与重试 | 弱网市场（东南亚）必调 |
| `circuit_breaker` | 连续失败 N 次后熔断 M 秒 | **保护 AdMob 账号**，避免无效请求被判为无效流量 |
| `max_ad_content_rating` | 广告内容分级（G / PG / T / MA） | 受众合规 |
| `tag_for_child_directed` | 儿童向标识 | Play 家庭政策；设错会直接导致 AdMob 停号 |
| `npa`（非个性化广告） | 同意未获取时降级为非个性化 | EEA/UK GDPR；东南亚暂无强制但 Play 政策建议支持 |
| `kill_switch` | 全局一键关广告 | 出事故时 5 分钟内止血 |

### 2.3 配置数据结构示例

```json
{

    },
    "interstitial_after_calibration": {
```

## 三、接口与链路设计

### 3.1 与埋点配置**必须解耦**

- 不要复用 `/api/v1/analytics/config`。原因：该端点受埋点开关与埋点认证约束，而**广告是变现链路，用户关闭埋点后广告仍应正常展示**。这正好落实 10.1 原则 5「与广告系统隔离」。
- 建议新增：`GET /api/v1/config/ads`（Bearer Token，与匿名设备 Token 复用）或统一 `GET /api/v1/remote-config?modules=ads,analytics`（模块化解耦，单次请求，减少 RTT）。

### 3.2 拉取与缓存策略

| 项 | 建议 |
|---|---|
| 拉取时机 | 冷启动；前后台切换且距上次拉取 > TTL（建议 1 小时）；推送唤醒时 |
| 增量更新 | 请求带 `If-None-Match: {config_version}`，服务端无变更返回 304，省流量 |
| 本地缓存 | 上次成功配置持久化，启动时**先用缓存**再异步更新（保证首屏有广告可用） |
| 降级链 | 服务端失败 → 本地缓存 → 内置 L0 默认值 → 该广告位关闭（**绝不允许用空/错误 ID 狂刷**） |
| 安全 | 强制 HTTPS；建议服务端对配置体签名（或至少校验 Play Integrity / 包名 + 版本），防止中间人替换 `ad_unit_id` 导致**收入被劫持** |

### 3.3 客户端容错（必须写进 PRD）

1. `ad_unit_id` 格式校验（`ca-app-pub-...`），非法值视为"该位关闭"并上报 `ad_config_invalid` 异常事件；
2. 熔断：某单元连续加载失败达阈值 → 冷却期内不再请求，冷却结束试探性恢复；
3. 配置版本回滚：管理平台支持一键回退到上一版本；
4. 所有配置异常（拉取失败、解析失败、校验失败）需**独立埋点告警**，接入 F-010 的异常事件体系。

## 四、管理平台需要具备的能力

| 能力 | 说明 |
|---|---|
| 广告位 CRUD | 新增/编辑/停用广告位，绑定 unit_id、平台、频次、场景 |
| 多维下发 | 按国家、App 版本范围、用户分群（Pro/免费/新用户）下发不同配置 |
| 灰度发布 | 5% → 20% → 100% 逐步放量，异常可秒级回滚 |
| 紧急熔断 | 全局 `kill_switch` 与单广告位开关，目标 5 分钟内生效 |
| **变更审计日志** | 谁、什么时候、改了什么、改前改后值 —— 广告配置误操作是直接损失收入的事故，必须有审计 |
| 效果闭环 | 下发后直接看该 `placement_id` 的展示量、填充率、`ad_load_failed` 率、eCPM 变化（与 F-010 埋点打通） |
| 双人复核（可选） | 生产环境 `kill_switch` 与 unit_id 变更需二次确认 |

### 技术选型建议

| 方案 | 成本 | 适用 |
|---|---|---|
| **A. Firebase Remote Config**（推荐 MVP） | +3~5 天 | 自带控制台、国家/版本/随机百分比条件、灰度与回滚；App 已接 AdMob，依赖 Firebase 合理。**审计日志较弱**，需补录到自家后台 |
| **B. 自建（Laravel + 管理后台）** | +1.5~2 周 | 已有 Laravel 团队；审计、分群、与自家订单/投放系统打通更彻底。可与 F-010 的配置端点共用基础设施 |
| **C. 混合** | — | 广告配置走 Firebase RC（快、稳），业务配置自建；两套配置 SDK 封装成统一 `RemoteConfig` 门面，业务侧无感 |

> 个人建议：**MVP 用 A，配置门面抽象好，V2 再平滑切到 B**，避免前期为配置系统投入过多工期。

## 五、对埋点事件的连带修改（重要）

当前 `banner_impression` / `banner_clicked` / `interstitial_impression` / `interstitial_closed` 只带 `ad_unit_id`。建议改为**同时携带稳定维度**：

| 属性 | 说明 |
|---|---|
| `placement_id` | **新增**，稳定标识（如 `banner_home`）。看板按此聚合，换 unit_id 后历史连续 |
| `ad_unit_id` | 保留，用于与 AdMob 后台对账 |
| `config_version` | 新增。配置灰度期间可按版本对比效果 |
| `network` / `ad_source` | 新增/预留。接入聚合后必需，否则无法做 waterfall 分析 |
| `revenue_micros` / `currency` / `precision_type` | 新增。呼应评审 P0-1 的 eCPM 缺失（来自 AdMob `OnPaidEventListener`） |

## 六、合规补充

- `ad_unit_id` 变更若伴随数据收集范围变化（如启用个性化广告、使用 AAID），需同步更新 **Google Play Data Safety 表单**；
- `tag_for_child_directed` 与 `max_ad_content_rating` 设错会被 AdMob 直接停号，必须**服务端可控 + 变更需双人复核**；
- 用户撤回广告个性化同意时，应能远程下发 `npa: true` 全局降级，而非发版；
- 广告配置下发请求本身不应携带可识别个人信息，`country` 取国家级别即可（不采集精确位置，符合 10.6.1）。

---

## 七、建议写入 PRD 的验收标准

| # | 验收项 |
|---|---|
| 1 | 不发版修改任一 `ad_unit_id`，**15 分钟内** 90% 以上活跃客户端生效 |
| 2 | 管理平台触发 `kill_switch` 后，**5 分钟内** 95% 以上客户端停止广告请求 |
| 3 | 服务端不可达 + 本地缓存为空时，App 使用内置默认配置正常展示广告，不出现空 ID 请求 |
| 4 | 某单元连续失败达阈值后触发熔断，冷却期内请求量降为 0（抓包验证） |
| 5 | Pro 用户（或 `is_pro=true` 分群）全局不出广告，且不影响埋点上报 |
| 6 | 用户关闭埋点开关后，广告配置仍能正常拉取、广告正常展示 |
| 7 | 所有配置变更有审计日志，可追溯操作人与前后值 |

---

## 八、工期影响

在上一版评审"+4~5 周"基础上：

- 方案 A（Firebase RC）：**+3~5 天**（含客户端配置门面、降级链、熔断、埋点属性改造）
- 方案 B（自建）：**+1.5~2 周**（含管理后台 CRUD、灰度、审计日志、下发接口）
- 若采用方案 B，可与 F-010 的 Laravel 配置端点**共用基础设施**，边际成本可压缩到 +1 周左右

> 无论选哪个，**客户端的配置门面 + 三级降级链 + 熔断**这部分是必须的，约 3 天，不能省。
